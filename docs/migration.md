# 旧账本迁移、备份和恢复

引擎源码和个人数据是两个目录。下面命令从引擎源码目录运行，`~/health-data` 仅为示例；
换成用户自己的持久目录。云电脑应选可持久挂载的私人目录，不把工作区或 `/tmp` 当正式数据。
更新程序不会自动迁移个人账本，以下步骤由用户或其授权的 AI 对选定账本执行。

## 格式 1 → 格式 2

新引擎继续读取格式 1 的饮食、体重、计划、默认品种、用户食品库及其原始签名。
旧的自然语言写入命令已退役。启用结构化意图写入前，运行：

```sh
python3 scripts/hl.py --data ~/health-data migrate
python3 scripts/hl.py --data ~/health-data migrate --apply
python3 scripts/hl.py --data ~/health-data check
```

第一条只预检，不改账本，不自动修复缺失来源或重建清单。坏签名、账实不符、缺密钥、
错误路径或符号链接都会阻止迁移；按诊断从原备份恢复，不要删掉报错文件或重新签名。
如果有未完成的事务，命令会先根据签名正确的事务日志回滚，恢复到上次完整状态。

`--apply` 在同一账本锁内执行以下步骤：

1. 再次预检，复制整个目录到同一父目录下新的 `<原目录名>.backup-<唯一编号>`。
   包含 `.hl/`、原话、密钥、缓存、审计及 Git 文件；不覆盖已有目录。
2. 逐文件核对备份 SHA256，并把备份写入持久存储。备份目录权限设为仅当前用户可访问。
3. 在事务中把 `hl.toml` 的格式标记更新为 2，创建签名的 `.hl/intents.json`，
   并在签名清单中记录采用的协议版本。只恢复旧配置或删掉操作历史不能把新账本伪装成旧账本。
   旧饮食、计划、体重、默认品种和用户库文件原字节保留，不重签、不补造原话出处。
   同时生成 `HEALTH_LOG_V2.md` 新指南，在原 `AGENTS.md`、`CLAUDE.md` 前加入新指南指针。
4. 再次校验。失败则还原格式标记和操作历史，旧记录不变，保留完整备份。

完成输出中的 `backup` 是真实备份路径。再次运行不会重复迁移或覆盖操作历史。
同磁盘备份便于回退，但不能代替另一块持久磁盘或私人存储上的灾难恢复备份。

迁移会自动升级 Agent 的阅读入口：`HEALTH_LOG_V2.md` 取自当前
[新 Agent 指南模板](../src/hl/data/templates/AGENTS.md)，原 `AGENTS.md`、`CLAUDE.md`
的全部内容保留在指针之后，原字节也保存在完整备份里。指针明确旧写入协议、逐字匹配、
先删后重记和强制 hooks 规则已被取代，个人业务偏好继续保留。让 Agent 在迁移完成后重读
指南即可。宿主配置不自动覆盖，旧 hooks 可以移除，正常流程不依赖它们。
这几份指南与版本标记一同提交或回滚；`init` 不会强制覆盖现有指南，不能靠重复 `init` 完成升级。

旧账的 `e1` 等编号只在各自日期内唯一，迁移时仍原样保存。首次明确更正某条旧记录时，
引擎才给该条记录分配全局身份；结果的 `previous_target` 和签名审计保留原日期、编号和版本。
以后更正或跨日移动沿用这个新身份，目标日同编号的其他旧记录不受影响。

## 搬到另一台电脑

停止向账本写入，运行 `check`，完整复制数据目录并带上隐藏文件，再复制或下载引擎源码。
在新电脑按 [最小安装](portable-install.md) 准备 Python 和依赖，然后使用明确的数据路径：

```sh
python3 scripts/hl.py --data /你的持久目录/health-data check
python3 scripts/hl.py --data /你的持久目录/health-data recent
```

不要复制旧电脑的 `.venv`，在新系统重新引导环境。账本的 `.hl/secret` 和
`.hl/intents.json` 必须随数据一起带走，不能重新生成。已有缓存可离线使用；缓存没有带全时，
按诊断下载或构建相同食物版本，不能将已有的精确营养记录当成估算来绕过检查。
Git 可选；单独复制 Git 跟踪文件不够，因为 `.hl/` 不进 Git。

## 回退

没有自动覆盖整个账本的 `--restore` 命令。回退前停止所有 Agent 写入，先把当前目录另存一份，
避免丢失迁移后新增的记录。保留原目录，不把备份中的个别文件拼到当前账本里。

可以把 `--data` 改为迁移输出的完整备份目录，先运行 `check` 和 `recent` 核对；
也可以把整个备份复制到一个新的私人持久目录再核对。格式 1 的备份仍可由新引擎查询，
若要继续结构化写入，需对选定的恢复副本重新迁移。迁移前后的两份账本不会自动合并；
迁移后有新记录时，由 Agent 先比较完整历史，再决定补录哪些真实事件。

## 写入中断

格式 2 的多文件操作使用同一把锁和 `.hl/transaction.json` 签名回滚日志。
操作前原始文件已写入日志，命令成功前会把记录、清单、操作收据和历史一起提交。
异常或进程退出后，下次命令先恢复原始文件，再允许查询或写入。
首次 `init` 的配置、清单和操作历史也一同提交；初始化中断后可重试 `init` 恢复，
不会把已经使用过却遗失历史的账本当作新账重建。
恢复日志签名无效、路径异常或恢复失败时会停止，不采纳半成品，也不自动删除日志。

同一次工具重试必须使用原 `request_id`；实际提交过的操作返回 duplicate，不重复记账。
original_result 保留当时结果，current/current_status 说明目前是否已更正或删除，不能将历史数量说成现状。
修改操作绑定记录当前版本，其他 Agent 已改过时会拒绝覆盖；查询新版本后再判断原更正是否仍适用。
每次设置更正产生独立签名版本；数值改回旧值，也不会让之前的旧版本重新有效。
这些检查防止误操作和不一致，不能证明 Agent 理解一定正确，也不能阻止拥有本机全部权限的人伪造数据。
