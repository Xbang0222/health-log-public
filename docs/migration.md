# 旧账本迁移、备份和恢复

新使用方式是一份私有项目同时保存程序与账本。下面默认从自己的项目根目录运行，
`python3 scripts/hl.py` 使用该项目根目录，不依赖 `HL_DATA`。更新程序不会自动迁移数据。
已有外部账本仍可用显式 `--data /原账本` 操作；所有步骤只针对用户选定并授权的目录。

## 将旧账本归入已有私有项目

如果程序和账本曾分开保存，最终使用位置是**已有的私有 `health-log` 仓库**。
把旧账本完整归入这里，不再往旧账本目录安装一套程序，也不另建使用副本。
目录合并与格式 1 → 2 是两件事，不能通过改格式号完成迁移。

1. 停止两边写入，检查并完整备份旧账本和目标私有项目，包括隐藏文件。
2. 核对目标是否已有账本。若有同名配置、业务文件或 `.hl`，先确认要保留的完整账本状态，
   不能把两套签名账本拼接或直接覆盖。目标原有程序、食品数据、私有开发历史继续保留。
3. 完整复制旧账本的 `hl.toml`、全部业务文件（`log/`、计划、默认、个人 `foods/` 等）、
   整个 `.hl` 和个人规则；不覆盖目标的 `.git`、`.venv` 或程序文件。
   保留旧指南原文，个人偏好合并到私有 `PERSONAL_RULES.md`，根 `AGENTS.md` 保持通用入口。
4. 数据签名不绑定项目的绝对根路径，无需因搬目录重签。核对迁移后本地食品原始数据的位置；
   配置里的 raw 路径用于修复提示，不是正常记账必须继续保留旧根目录的理由。有效食品缓存先校验复用。
5. 在目标项目准备依赖，运行 `python3 scripts/hl.py check`、`doctor` 和 `recent`，核对实际记录。
   需要格式升级时按下一节预检和执行。确认成功后将旧目录归档并停止向它写入，以后只打开目标项目。

另需核对旧 hooks：旧 `init --hooks` 的宿主 handler 和 Git pre-commit 调用全局 `hl`。
默认不启用旧宿主 hooks；先备份，仅移除已确认属于旧模板的 handler，保留自定义钩子和权限设置。
Git pre-commit 若保留，须定位当前仓库根调用本地 `scripts/hl.py`，保留 `.hl` 禁止入 Git 和 check 失败拒绝提交。
旧 hooks 模式需另行适配并验证实际宿主，不能仅因目录合并就宣称兼容；未核验原话采集时来源仍是 `agent-reported`。

这里描述的是迁移方法，不表示任何现有个人账本已经迁移。复制或下载程序不会自动移动个人数据。

## 格式 1 → 格式 2

新引擎继续读取格式 1 的饮食、体重、计划、默认品种、用户食品库及其原始签名。
旧的自然语言写入命令已退役。启用结构化意图写入前，运行：

```sh
python3 scripts/hl.py migrate
python3 scripts/hl.py migrate --apply
python3 scripts/hl.py check
```

命令先恢复必要的未完成事务，再完整校验账本。已经是格式 2 时，还会验证操作历史，
通过后直接返回“无需迁移”：不再扫描整个项目制作迁移备份、不更新指南，也不覆盖历史。
因此格式 2 的校验失败不会被“已经迁移”掩盖。

格式 1 的第一条命令只做预检，不改格式，不自动修复缺失来源或重建清单。
坏签名、账实不符、缺密钥、错误路径，以及需要备份内容中的符号链接或特殊文件都会阻止迁移；
按诊断处理或从原备份恢复，不要删掉账本文件或重新签名来消除报错。
未完成事务的恢复依据签名正确的事务日志，将数据恢复到上次完整状态。

格式 1 备份唯一允许排除的是项目根 `.venv`：它必须是普通目录，且其中的 `pyvenv.cfg`
必须是普通文件，才按可重建的 Python 环境处理。这一目录不再递归备份或检查其内部解释器链接。
`.venv` 本身是链接、不是目录，或缺少普通 `pyvenv.cfg` 时会阻止预检，不能仅凭目录名排除内容。
其他程序文件、个人数据、隐藏文件和指南都在备份范围；其他位置的链接仍会阻止迁移。
预检和迁移结果中的 `excluded` 会如实列出本次排除项。

`--apply` 在同一账本锁内执行以下步骤：

1. 再次预检，按上述范围复制项目到同一父目录下新的 `<原目录名>.backup-<唯一编号>`。
   除满足条件的根 `.venv` 外，包含程序、`.hl/`、原话、密钥、缓存、审计、Git 文件与个人指南；
   不覆盖已有目录，恢复后可运行 bootstrap 重建环境。
2. 逐文件核对备份 SHA256，并把备份写入持久存储。备份目录权限设为仅当前用户可访问。
3. 在事务中把 `hl.toml` 的格式标记更新为 2，创建签名的 `.hl/intents.json`，
   并在签名清单中记录采用的协议版本。只恢复旧配置或删掉操作历史不能把新账本伪装成旧账本。
   旧饮食、计划、体重、默认品种和用户库文件原字节保留，不重签、不补造原话出处。
   同时生成 `HEALTH_LOG_V2.md` 新指南，在原 `AGENTS.md`、`CLAUDE.md` 前加入新指南指针。
4. 再次校验。失败则还原格式标记和操作历史，旧记录不变，保留完整备份。

完成输出中的 `backup` 是真实备份路径。再次运行不会重复迁移或覆盖操作历史。
同磁盘备份便于回退，但不能代替另一块持久磁盘或私人存储上的灾难恢复备份。

格式 1 迁移会升级 Agent 的阅读入口：`HEALTH_LOG_V2.md` 先放入当前
[Agent 指南模板](../src/hl/data/templates/AGENTS.md)。如果原来已经有不同的自定义正文，
其原字节完整追加到“保留的原指南与个人偏好”部分，不被新版正文丢弃；原文已与模板一致时不重复追加。
原 `AGENTS.md`、`CLAUDE.md` 的全部内容保留在新指针之后，各份原字节也在备份中。
旧写入协议、逐字匹配、先删后重记和强制 hooks 等冲突规则由新契约取代，不冲突的个人偏好继续遵守。
迁移后让 Agent 重读指南。宿主配置不自动覆盖，旧 hooks 可以移除，正常流程不依赖它们。
这些指南与版本标记一同提交或回滚。

新项目 `init` 创建格式 2 账本时会补齐 `HEALTH_LOG_V2.md`；已有有效格式 2 账本缺少这份指南时，
`init` 在完成校验后也可补齐。已经存在的指南正文不覆盖，因此它不是更新个人规则的工具，
也不能靠重复 `init` 把格式 1 升级为格式 2。

旧账的 `e1` 等编号只在各自日期内唯一，迁移时仍原样保存。首次明确更正某条旧记录时，
引擎才给该条记录分配全局身份；结果的 `previous_target` 和签名审计保留原日期、编号和版本。
以后更正或跨日移动沿用这个新身份，目标日同编号的其他旧记录不受影响。

## 搬到另一台电脑

停止写入并运行 check，完整复制自己的项目，包括程序、个人规则、记录和隐藏的 `.hl`。
不要只复制 Git 跟踪文件或 `log/`。`.venv` 可以不带，它包含旧电脑的路径和平台文件。
在新电脑打开这一目录，按[安装说明](portable-install.md)准备 Python，再运行：

```sh
python3 scripts/bootstrap.py
python3 scripts/hl.py check
python3 scripts/hl.py doctor
python3 scripts/hl.py recent
```

`.hl/secret` 和 `.hl/intents.json` 必须随项目带走，不能重新生成。
已有食品缓存先校验，可用则离线复用；缺失时按诊断从保留的原始数据构建或下载对应版本，
不能将原有精确营养记录改称估算来绕过检查。搬家后核对本地原始数据路径，旧电脑的绝对路径可能不再可用。
私有 Git 可跟踪账本、设置、食品数据和个人规则，但 `.hl` 不进 Git。
`git push` 只同步已提交内容，完整私人备份仍须带上 `.hl` 和其他未跟踪文件；
新私有副本的跟踪配置见[保存与 Git 跟踪](publication.md#保存自己的项目)。

## 更新项目程序

先完整备份，再按[分发允许清单](publication.md)更新程序部分，不整目录覆盖或镜像删除。
保留账本配置、记录、计划、默认、个人食品、`.hl`、`PERSONAL_RULES.md` 及已有私有食品原始数据。
合并新版根入口规则后运行 bootstrap、check、doctor；bootstrap 只管理依赖，不升级数据格式。
如新版确实要求格式变化，按相应迁移步骤单独预检和执行。

## 回退

没有自动覆盖整个账本的 `--restore` 命令。回退前停止所有 Agent 写入，先把当前目录另存一份，
避免丢失迁移后新增的记录。保留原目录，不把备份中的个别文件拼到当前账本里。

可以用当前程序显式指定 `--data /迁移输出的完整备份目录`，先运行 `check` 和 `recent` 核对；
也可以把整个备份复制到一个新的私人持久目录再核对。格式 1 的备份仍可由新引擎查询，
若要继续结构化写入，需对选定的恢复副本重新迁移。迁移前后的两份账本不会自动合并；
迁移后有新记录时，由 Agent 先比较完整历史，再决定补录哪些真实事件。

## 写入中断

格式 2 的多文件操作使用同一把锁和 `.hl/transaction.json` 签名回滚日志。
操作前原始文件已写入日志，命令成功前会把记录、清单、操作收据和历史一起提交。
异常或进程退出后，下次命令先恢复原始文件，再允许查询或写入。
首次 `init` 的配置、清单和操作历史也一同提交；初始化中断后可重试 `init` 恢复，
不会把已经使用过却遗失历史的账本当作新账重建。
恢复日志签名无效、路径异常或恢复失败时会停止，不采纳半成品，也不自动删除日志。

同一次工具重试必须使用原 `request_id`；实际提交过的操作返回 duplicate，不重复记账。
original_result 保留当时结果，current/current_status 说明目前是否已更正或删除，不能将历史数量说成现状。
修改操作绑定记录当前版本，其他 Agent 已改过时会拒绝覆盖；查询新版本后再判断原更正是否仍适用。
每次设置更正产生独立签名版本；数值改回旧值，也不会让之前的旧版本重新有效。
这些检查防止误操作和不一致，不能证明 Agent 理解一定正确，也不能阻止拥有本机全部权限的人伪造数据。
